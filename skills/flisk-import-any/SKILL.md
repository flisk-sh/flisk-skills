# Bring any existing service into TDK

Use this when you already have a Dockerfile, an image, a Procfile process, a Helm chart, a Terraform module, or any other service that should run locally under `tdk up`.

## Choose the path

- Root `docker-compose.yml` exists → use the `flisk-import-compose` skill (`tdk import .`).
- You have a Dockerfile or image for one service → use BYO (below).
- You have only source and a start command → write a small Dockerfile, then use BYO.
- You have a production Helm chart or Terraform → keep it for production. Use BYO or a scaffolded resource for local only. TDK does not replace Helm.

## BYO workflow

```bash
tdk resource <name> --type bring-your-own --stack <stack> \
  --dockerfile ./Dockerfile --health-path /health \
  --path services/<stack>/<name> --yes
```

Or with an image:

```bash
tdk resource <name> --type bring-your-own --stack <stack> \
  --image ghcr.io/example/service:latest --no-proxy --yes
```

## What the container must do

1. Listen on the port in `service.json` (read `PORT` from the environment).
2. Bind to `0.0.0.0` so Traefik can reach it.
3. Answer HTTP 200 on `healthCheckPath` if it speaks HTTP. Non-HTTP services (databases, brokers) can omit `healthCheckPath`.
4. Provide the image via `Dockerfile` or `--image`.

## One-shot jobs

For migrations or seeders set the restart policy so the container does not loop:

```bash
tdk resource migrate --type bring-your-own --stack shop \
  --dockerfile ./Dockerfile --restart no --yes
```

## Guardrails

- TDK does not generate application code for BYO. You own the Dockerfile and the health route.
- TDK injects `PORT` and `DATABASE_URL`. An app that validates the Host header or prefers its own database URL may need configuration.
- Resource names must be unique across TDK projects that share one Docker daemon.
- Do not hand-edit `.autogenerated/`. Change `service.json` and regenerate.
- Production stays on Helm, Terraform, or whatever you already use. TDK is local only.
